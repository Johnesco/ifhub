Versioning

How IF Hub keeps every milestone of a game playable — from raw port to polished release — so the progression itself becomes part of the experience. ← Back to Hub

Why Versions Matter Here

Most software ships the latest version and discards the rest. IF Hub does the opposite: every numbered milestone stays playable forever, side by side, on the same hub.

The reason is that the games we host often tell a story in their version history:

  • Translation portfolios — a classic ZIL game ported to Inform 7. v0 is the original Infocom build; v1 is the faithful port; v2 fixes bugs Infocom shipped; v3 adds sound and atmosphere. Each playable, each instructive.
  • Tutorial increments — a teaching game grows feature by feature. v1 covers conversation; v2 adds inventory; v3 adds NPCs with goals. A reader of the source learns by diffing the versions.
  • Authored revisions — the author wants their 2020 release preserved alongside their 2025 director’s cut. Players can pick either.

For this to work, every feature IF Hub offers must keep working for every version, not just the current one. A user clicking "Play v2" expects the same affordances as a user clicking "Play (Current)": a game that runs, a source they can read, a walkthrough they can follow, a transcript they can download.

The Repo Model

A multi-version project is one GitHub repo per version. The main repo is the working copy ("Current"); each frozen version lives in its own repo named <game>-vN.

Johnesco/zork1          ← Current (the working copy, no version number)
Johnesco/zork1-v0       ← Original engine (ZIL / BASIC / etc.)
Johnesco/zork1-v1       ← Frozen: faithful port
Johnesco/zork1-v2       ← Frozen: bug fixes / enhancements
Johnesco/zork1-v3       ← Frozen: multimedia / further enhancements

Each repo:

  • Is self-contained — story source, compiled binary, walkthrough, tests, web player. It can build and deploy on its own.
  • Deploys independently to its own GitHub Pages site (e.g. johnesco.github.io/zork1-v2/).
  • Is registered as a separate entry in the IF Hub registry, with a versionOf link back to the parent game.

The hub iframes each version’s GitHub Pages site into a unified browsable experience. The hub itself doesn’t host the games; it points at them and groups them.

The Version Philosophy (Common Pattern)

Each project defines its own promotion rules, but the recurring pattern is:

VersionEditing policyTypical purpose
v0Never touch.The original, exactly as released. Fixes are only ever applied in v1+.
v1Bugs only.Faithful 1:1 translation. No enhancements, no quality-of-life. Goal: gameplay matches v0.
v2Any fixes or enhancements.First version that intentionally changes the game. Bug fixes from the original engine, translation fixes from v1.
v3Multimedia & guidance.Sound, atmosphere, additional player hints — written sparingly to match the original’s style.
CurrentDefault work target.All new development. Will become the next numbered version when frozen.

Project-specific deviations belong in that project’s own CLAUDE.md.

Change Propagation

Changes only propagate upward, never downward. If a fix lands in vN, apply the same change to v(N+1), v(N+2), …, and Current. v1 stays "as v1 always was"; v2 inherits v1 plus its own fixes; and so on.

Cascade rule: each version is a strict superset of the one below it. v2 contains everything in v1 plus its own changes; v3 contains everything in v2 plus its own; Current contains everything from the topmost frozen version plus the work in progress.

The Per-Version Feature Contract

For IF Hub to expose its full UI for any version, that version’s repo must produce the following deliverables. These are the things authors need to keep up to date when patching a frozen version (rare) or when a new version is cut from Current (routine).

FeatureWhat the hub doesWhat the version repo provides
PlayLoads play.html into the hub’s player pane.play.html + compiled binary + base64 wrapper (e.g. lib/parchment/<game>-vN.ulx.js).
Source browserLoads source.html into the source pane.source.html rendering this version’s story.ni (or equivalent).
Walkthrough viewerLoads walkthrough.html — an annotated step-by-step guide.walkthrough.html + walkthrough.txt + walkthrough-guide.txt.
Transcript downloadLinks the deterministic play transcript.walkthrough_output.txt (generated by walkthrough runner with the version’s golden seed).
Version bannerShows the version label in the in-game banner.After printing the banner text rule (or equivalent) in the source: e.g. say "v2: Bug Fixes & Testing".
Group landingTop-level johnesco.github.io/<game>/ page lists all versions newest-first.Current repo’s landing.json describes Current; each frozen version contributes its own card via the hub registry.

Compile, walkthrough, and registry generation are all driven by ifhub.conf in each repo plus the central games-registry.json. The pipeline knows how to build, test, and re-register a single version:

python tools/pipeline.py <game>-v2 compile
python tools/pipeline.py <game>-v2 compile test
python tools/pipeline.py <game>-v2 --ship       # compile + test + register + publish + push hub

Hub Registration

Every entry — Current and each frozen version — is its own row in games-registry.json:

{
  "zork1": {
    "path": "../text-games/i7/zork1",
    "repo": "Johnesco/zork1",
    "versionPrimary": true,
    "versionPrimaryLabel": "Current"
  },
  "zork1-v1": {
    "path": "../text-games/i7/zork1-v1",
    "repo": "Johnesco/zork1-v1",
    "versionOf": "zork1",
    "versionLabel": "v1 — The Port"
  },
  "zork1-v2": { /* … */ },
  "zork1-v3": { /* … */ },
  "zork1-v0": {
    "path": "../text-games/zmachine/zork1-v0",
    "repo": "Johnesco/zork1-v0",
    "versionOf": "zork1",
    "versionLabel": "v0 — Original ZIL"
  }
}

Key fields:

  • versionOf — groups this entry under a parent game on the hub UI.
  • versionLabel — what shows in the version dropdown and side-by-side lists (e.g. "v2 — Bug Fixes").
  • versionPrimary: true — marks the Current entry that represents the top of its group.

Each version repo’s ifhub.conf is the source of truth for its own metadata; games-registry.json stores the cross-cutting path / repo / versionOf linkage. After changes:

python tools/register_game.py --name <game>-v2   # regenerates site/games.json and site/cards.json
python tools/push_hub.py                          # commits + pushes hub registry

Title Convention

Titles should make a version recognizable at a glance in any hub view — the version dropdown, the games list, search results, breadcrumbs. The recurring pattern is:

title = Zork I (Current)
title = Zork I (v0 — Original ZIL)
title = Zork I (v1 — The Port)
title = Zork I (v2 — Bug Fixes)
title = Zork I (v3 — Multimedia)

If a version’s title lacks the (vN — …) marker, the entry appears in flat lists as if it were a separate top-level game — producing the appearance of a duplicate. Keep titles consistent across all version entries in a project.

Deploy Path

Each repo deploys on git push via its own deploy-pages.yml workflow. The chain looks like this:

  1. Author edits story.ni in the version’s repo (or in Current, for routine work).
  2. pipeline.py compile rebuilds the binary, base64-encodes it into lib/parchment/<game>-vN.ulx.js, regenerates play.html / source.html / walkthrough.html.
  3. pipeline.py test reruns the walkthrough (deterministic via the version’s golden seed in tests/seeds.conf) and regenerates walkthrough_output.txt + walkthrough-guide.txt.
  4. Commit + push to the version repo. GitHub Actions deploys to johnesco.github.io/<game>-vN/ within ~30s–2 min.
  5. The hub picks up the new content automatically next page load — its iframes point at the GitHub Pages URLs.

If hub registry data changed (title, description, version label), also re-run register_game.py and push the IF Hub repo so the hub UI sees the update.

What the Per-Version Repo Looks Like

A minimal, working per-version repo should contain:

  • ifhub.conf — engine, title (with version marker), binary name, tags, version metadata
  • story.ni — frozen source for this version
  • <game>-vN.ulx or .gblorb — compiled binary
  • play.html — Parchment (or engine-specific) player
  • source.html — source browser pointed at this story.ni
  • walkthrough.html — walkthrough viewer iframe
  • walkthrough.txt — raw commands
  • walkthrough-guide.txt — annotated guide (generated)
  • walkthrough_output.txt — full transcript (generated)
  • lib/parchment/ — engine files + base64 binary for the web player
  • tests/project.conf — test runner config
  • tests/seeds.conf — this version’s golden seed (may differ between versions because RNG paths diverge)
  • CLAUDE.md — "this version is FROZEN" marker + reference to the central guide
  • .github/workflows/deploy-pages.yml — GH Pages deploy

Common Mistakes

  • Editing a frozen version when you meant to edit Current. Default work goes into the main repo (Current). Check pwd before editing story.ni.
  • Forgetting to propagate upward. A bug fix in v2 must also be applied to v3 and Current. The cascade isn’t automatic.
  • Editing a .ulx / .gblorb directly. Always edit story.ni and recompile. The base64 wrapper for the web player is regenerated by the pipeline.
  • Stale binaries. A version’s story.ni and its compiled binary must match. If you change source, recompile that repo before committing.
  • Reusing one walkthrough seed. Different versions need different golden seeds; check each repo’s tests/seeds.conf.
  • Inconsistent titles. If a version’s title lacks (vN — …), the entry can look like a separate top-level game in dropdowns. Match the sibling pattern.
