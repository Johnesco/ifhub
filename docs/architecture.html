IF Hub Multi-Engine Architecture

A hybrid push architecture for independent game development with push-button showcase publishing

Core Principle

Workspaces own build. A shared CLI owns ship. Each engine workspace compiles, tests, and previews games independently. IF Hub is only needed for the final "publish to showcase" step.

IF Hub is a jukebox — a portfolio that showcases interactive fiction at the push of a button. It is not a build system. Each engine has its own dev environment, compiler, and workflow. The hub just aggregates and displays finished work.

The Export Contract

Every engine workspace must produce a deploy-ready directory. This is what ship.py expects:

Required
<game>/
  ifhub.conf          # Manifest: engine, title, author, tags, source, binary
  play.html           # Playable game (self-contained web player)
Optional (ship.py generates if missing)
  source.html         # Syntax-highlighted source viewer
  walkthrough.html    # Formatted walkthrough
  index.html          # Landing page
  walkthrough.txt     # Raw walkthrough commands
  lib/                # Runtime assets (Parchment, ink.js, etc.)
  src/                # Source files (for Sharpee multi-file projects)

The ifhub.conf manifest is the only protocol between workspaces and the hub:

engine = inform7
title = Dracula's Castle
author = An Interactive Adventure
description = Explore Dracula's Castle and uncover its dark secret.
binary = dracula.ulx
source = story.ni
walkthrough = walkthrough.txt
tags = horror, classic

The Shared Ship CLI

ship.py is the only tool workspaces need from ifhub. It consolidates three existing scripts into one:

What it does
  • Reads ifhub.conf from game dir
  • Generates source.html (syntax-highlighted viewer)
  • Generates walkthrough.html (if walkthrough.txt present)
  • Generates index.html landing page (if missing)
  • Publishes to GitHub Pages (git init, push, enable Pages)
  • Registers in hub (updates games.json + cards.json)
  • Pushes hub changes to GitHub
What it does NOT do
  • Compile source code
  • Run tests
  • Generate play.html
  • Copy runtime assets (Parchment, ink.js)
  • Know anything about engine internals

Those are the workspace's responsibility. ship.py treats every game as a black box with ifhub.conf + play.html. 

# From any game directory:
python /c/code/ifhub/tools/ship.py dracula

# Or via the convenience pipeline (delegates build to workspace, then ships):
python /c/code/ifhub/tools/pipeline.py dracula --ship

Shared Asset Strategy

Runtime assets (Parchment, templates, theme-listener.js) are vendored into each workspace so builds have zero ifhub dependency. ifhub remains the canonical source.

sync_assets.py

Pushes canonical versions from ifhub/tools/web/ to all workspaces. Run only when assets change (~annually for Parchment, quarterly for templates).

python /c/code/ifhub/tools/sync_assets.py           # sync all workspaces
python /c/code/ifhub/tools/sync_assets.py i7         # sync one workspace

This is a push from ifhub, not a pull from workspaces. Workspaces never reference ifhub paths at build time.

Play templates (7 variants) ifhub/tools/web/templates/ each engine gets its own ~quarterly

Game Discovery (3-Layer)

Layer 1: workspaces.json convention

Scans workspace roots for subdirs with ifhub.conf. No per-game entries needed.

{ "workspaces": [
  { "engine": "inform7",
    "root": "../text-games/i7",
    "deploy": "in-place" },
  { "engine": "sharpee",
    "root": "../npmsharpee/games",
    "deploy": "../text-games/deploy" }
]}
Layer 2: games-registry.json overrides

Explicit entries for edge cases. Overrides workspace discovery. Also stores GitHub repo references.

{ "dracula": {
    "path": "../text-games/i7/dracula",
    "repo": "Johnesco/dracula"
  }
}
Layer 3: games-local.json per-developer

Gitignored. Personal path overrides without affecting the repo. Rarely used.

Migration Phases

Phase 1: Build Scripts additive, zero risk

Create tools/build.py in each engine workspace. Existing ifhub scripts continue to work unchanged.

Phase 2: Vendor Assets additive, zero risk

Copy Parchment, templates, theme-listener.js into workspace tools/assets/ directories. Create sync_assets.py.

Phase 3: Decouple I7 Test Tools medium risk

Update 16 scripts in i7/tools/ to import from local lib/. Transition fallback keeps old path working.

Phase 4: Create ship.py additive

Consolidate publish.py + register_game.py + push_hub.py into one CLI. Existing scripts still work.

Phase 5: Pipeline Delegation medium risk

Update pipeline.py to call workspace build.py first, with legacy fallback.

Phase 6: Documentation zero risk

Update all CLAUDE.md files to document self-contained workflows.
